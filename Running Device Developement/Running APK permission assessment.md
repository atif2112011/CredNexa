# Running APK permission assessment

**Implement all permissions and settings in this table that are marked as required, reliability features/options, or future use in the current CredNexa running borrower APK's permission checklist.** These labels describe their purpose; they are not reasons to omit or defer the permission flow. Include the checklist entry, explanation, permission request or supported Settings navigation, and actual status check for each applicable item, including Write Setting for future use. Exclude only entries explicitly marked as skipped, such as Usage Access and phone permissions. Show the purpose of each requested access and recheck its actual Android status when the borrower returns from Settings.

**If any doubt, missing requirement, unsupported behavior, or conflict with the existing app/API contract arises during implementation, ask the senior developer for clarification. Do not invent behavior, permission requirements, workarounds, or success states, and do not silently drop an item from the implementation.** Resolve unclear details, such as the Accessibility-service purpose or OEM battery-setting mapping, with the senior developer. Checklist inclusion does not automatically make an item an enrollment blocker: the current backend requires fresh notification and overlay reports; Device Admin remains optional. Confirm any additional blocking requirement with the senior developer before implementing it. Implement access marked for future use now; confirm the associated future behavior separately before enabling it.

| Permission / setting | Android mechanism and purpose | Use in CredNexa | Implementation decision |

| **Location Permission** | `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION` provide foreground access. `ACCESS_BACKGROUND_LOCATION` is a separate grant on supported versions; Android background execution rules also apply. [Background location](https://developer.android.com/develop/sensors-and-location/location/permissions/background) | Obtain location when a backend location command arrives while the app is in the background, subject to borrower consent and available access. | **Required for the intended background Get Location feature.** Request foreground access first, then background access through the version-appropriate flow. Confirm acceptable accuracy and whether denial blocks onboarding with the senior developer; the current backend does not enforce location as an activation requirement. Report denied/unavailable access accurately rather than returning stale coordinates as a fresh fix. |
| **Auto Start** | Usually an OEM-specific startup/background switch. `RECEIVE_BOOT_COMPLETED` is a separate manifest permission; reboot recovery also depends on applicable Android background-start rules. | Restore the running lock overlay after restart when the device remains locked, matching the observed King Locker behavior. | **Implement reboot recovery and include applicable OEM Auto Start guidance.** Restore the persisted lock state when Android permits startup; ensure unlock/release clears that state. Ask about unsupported OEM settings or startup restrictions rather than assuming universal recovery or displaying a grant that cannot be verified. |
| **Accessibility Permission / Allow restricted settings** | An Accessibility service is a separate user-enabled capability. **Allow restricted settings** is a manual Android App info action; Accessibility permission does not grant it or bypass Android's restriction. | Provide instructions when Android blocks overlay or other supported special access. The user confirmed this procedure restored overlay access on their Android 16 phone. | **Implement manual restricted-settings guidance.** Open **Settings → Apps → CredNexa borrower app → ⋮ → Allow restricted settings**, complete Android's confirmation, then return to the blocked permission and explicitly enable it. This action alone does not grant overlay or activate Accessibility. Ask the senior developer for the actual Accessibility-service use case before adding or requiring that service; do not invent one to clear this restriction. [Google instructions](https://support.google.com/android/answer/12623953) |
| **Write Setting** | `WRITE_SETTINGS` special access, checked with `Settings.System.canWrite()`, permits changes to supported system settings such as `SCREEN_OFF_TIMEOUT`; it does not grant access to secure settings. Audio volume uses `AudioManager` and has separate restrictions, including Do Not Disturb. [System settings](https://developer.android.com/reference/android/provider/Settings.System), [Audio controls](https://developer.android.com/reference/android/media/AudioManager) | Proposed future behavior: increase screen timeout and adjust reminder/lock sound while the overlay is active, then restore previous values when it is removed. | **Implement the permission flow now for future use.** Include this entry in the current checklist, explain its intended use, open the supported Write Settings screen, and check `Settings.System.canWrite()` on return. Agree on timeout, audio level, and restoration behavior with the senior developer before enabling those setting changes. Save prior values and define safe restoration when the borrower changes them or the app restarts. Write Settings access is not needed solely to play reminder sound. |
| **Battery Power Usage** | The photographed label does not identify one standard Android permission. It may refer to Android's per-app battery mode or OEM background/power settings, potentially overlapping Battery Optimization. | Reduce battery-related background restrictions that can interrupt command handling or overlay recovery. This is not a setting that prevents a user from force-stopping the app. | **Implement now as a reliability feature with supported per-app battery guidance.** Ask the senior developer which setting this row should open and whether it duplicates Battery Optimization. Do not invent a “screen battery optimisation” permission or show a universal granted state for an unverified OEM setting. |
| **Device Admin Permission** | User activation of the APK's `DeviceAdminReceiver` adds an admin-deactivation step before ordinary uninstall. AOSP Settings also restricts ordinary Clear Data for an active admin without a custom storage-management activity. [AOSP implementation](https://android.googlesource.com/platform/packages/apps/Settings/+/master/src/com/android/settings/applications/AppStorageSettings.java) | Add friction to uninstall and data clearing. The borrower can deactivate Device Admin in Settings, after which these protections can be removed. | **Request during onboarding, but allow enrollment if declined or restricted.** Check `DevicePolicyManager.isAdminActive()`. Verify Force Stop and Clear Data behavior on supported Android/OEM versions before claiming they are blocked. Do not use `lockNow()`; CredNexa's running lock is an overlay. |
| **Usage Access Permission** | `PACKAGE_USAGE_STATS` with user-enabled Usage Access permits reading app usage information. | CredNexa does not need other apps' usage details for the agreed running-device features. | **Skip.** Do not request it or make it an enrollment requirement. |
| **Overlay Permission** | `SYSTEM_ALERT_WINDOW`, checked with `Settings.canDrawOverlays()`; `TYPE_APPLICATION_OVERLAY` displays the running lock/reminder UI. | Retain the overlay implementation reported as already present in the current CredNexa running APK. Show EMI details, Pay Now, and Temp Unlock according to existing dealer-mode rules. | **Required for current running activation.** Recheck access after returning from Settings. If Android blocks the toggle, show the manual restricted-settings instructions in the Accessibility row. Overlay access does not provide Device Owner kiosk privileges. |
| **Runtime Permission** | Individual runtime grants, including `POST_NOTIFICATIONS` on Android 13+. Notification posting is separate from Notification Listener access. | CredNexa needs notifications for reminders. Phone access is unnecessary because IMEI values are entered manually. | **Request notification access; skip phone permissions.** Verify that notifications are enabled, including on older Android versions. Continue to request camera access when scanning a QR and location access as described below; skipping phone permission does not mean skipping every runtime permission. |
| **Battery Optimization** | Doze/App Standby exemption, checked using `PowerManager.isIgnoringBatteryOptimizations()`. Reduces some background restrictions; it does not prevent process termination, user force-stop, or every OEM battery restriction. [Android guidance](https://developer.android.com/training/monitoring-device-state/doze-standby) | Improve background reliability for command handling, reminders, and overlay recovery. | **Implement now as a reliability feature in the checklist.** Explain the benefit and open the supported battery settings. Check the actual exemption on return; do not promise that the app cannot be closed. |
