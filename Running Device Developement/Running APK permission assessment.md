# Running borrower APK: permission assessment

**Date:** 13 October 2026  
**Scope:** The ten rows photographed in the King Locker sample and discussed in `running_device_apk_analysis_and_architecture.md`, the user's subsequent real-device observations, and permissions that CredNexa's actual running flow needs. This is an assessment for the new CredNexa APK, not a claim that the sample APK's choices are correct. No code or enrollment rule was changed for this report.

## Executive finding

There is a real **scope difference** between the sample's permission checklist and the implemented CredNexa contract. The sample displays ten broad rows; CredNexa's current running-enrollment preview names only `notificationsAllowed` and `overlayAllowed` as required. `validateRunningCapabilities()` enforces those two fresh values during activation. Other access may be useful for a separately specified feature, but granting every photographed row would not turn an ordinary installed app into a Device Owner or guarantee a persistent lock.

The user's Android 16 test exposed a **release-critical onboarding constraint**: a downloaded APK can have **Display over other apps** blocked by Android Restricted Settings until the borrower explicitly approves restricted settings for that app in Android App info. The observed greyed-out switch and financial-risk warning fit this mechanism, and Android 16 expressly lists overlay access among the restricted settings. Disabling Play Protect scanning is a separate action and did not remove the block in the user's test. The app must handle this visibly because the current backend cannot activate a running device without a fresh overlay-access report.

The most important feature question is **Get Location**: a foreground-only location grant may work while the APK is visible, but is not a reliable basis for obtaining a fresh location after a remote command arrives while the app is in the background. The current backend permits `locationGrant: "foreground"` for that control. A requirement for unattended, fresh, on-demand location calls for a separate Android/background-location design and a corresponding backend capability rule. It should not be hidden inside a generic “Runtime Permission” checkbox.

## What the sample actually establishes

- The two photos show ten checklist labels. They show only “Write Setting” as green at the photographed moment. A green icon is app UI, not independent proof of an Android grant.
- The earlier static APK analysis found a native Android `PermissionActivity` that opens settings for Device Admin, Accessibility, Usage Access, overlay, write settings, and battery optimization. Its manifest contains **67 unique permission names**, including system/privileged permissions unavailable to an ordinary installed app. The subsequent user test is real-device observation, but no instrumented trace or permission-state capture was supplied.
- “Runtime Permission” and “Battery Power Usage” are **ambiguous labels**: the photos do not identify their exact grant or destination screen. “Auto Start” is typically an OEM setting rather than one portable Android permission.
- The new CredNexa APK is intended to reuse the existing borrower app. Its permission screen and Android manifest must be designed from CredNexa features, not copied from this unrelated sample.

### Permission-block diagnostic for a target phone

**Known now:** Android 16; overlay switch greyed out; tapping it shows the two warning lines above. **Confirmed follow-up on 13 October 2026:** The user manually selected **Allow restricted settings** using the documented App info route and reported that it worked, resolving the permission block on the tested phone. **Still unrecorded:** phone brand/model, APK install source, and whether that same confirmation happened during the original bottom-to-top sequence.

For a target-phone test, record the install source, exact warning/screenshot, whether the overlay switch is absent, greyed out, present but rejected, or later revoked, and the current `Settings.canDrawOverlays()` value. Check whether Android's **Allow restricted settings** option appears in App info; it is a **per-app user decision**, not a capability the APK or backend can silently grant. Record any OEM auto-start/power-control screen separately. A clean-install comparison can test the reported bottom-to-top sequence against another order on the **same model and Android build**, with a note of whether and when the restricted-settings confirmation occurred. This distinguishes a real order dependency from an earlier Android confirmation that happened during the sequence.

If the operating system or security software explicitly blocks the app or the grant, stop that activation attempt and investigate the warning, signing/distribution path, manifest, and app behavior. The borrower must be able to decline optional access. For the current backend contract, **overlay and notifications are required** at activation; Device Admin remains requested but optional. Since the planned running APK is downloaded through a link, Android 16's install-source rule is a **release-path risk**, not just a King Locker anomaly: test the exact CredNexa distribution and install path on Android 16 before release.

### Follow-up analysis: why bottom-to-top may appear to clear the block

**Finding:** The uploaded King Locker APK contains a concrete navigation difference that could explain the reported sequence: its bottom **Location Permission** row opens **Android App info** when location permission is missing. App info is also where Android provides the separate **Allow restricted settings** action. Starting from the top reaches the overlay restriction earlier; starting from the bottom can take the borrower to that App info page first. **Opening App info or granting location does not itself clear the restriction.** A separate Android confirmation, or some other state change on the tested phone, is still needed to explain a genuine overlay grant.

The user initially answered **“I don't remember”** when asked whether Allow restricted settings was used during the original bottom-to-top sequence. They then separately tested the manual App info route and confirmed that it worked. This validates the manual restricted-settings resolution on their Android 16 phone, while the exact events during the original sequence remain unknown.

**APK evidence, independently re-examined on 13 October 2026:** The uploaded sample still has SHA-256 `59DFC34CB73D3E59FE8AEBD6F97616F1C653A439E35817A1AB43E0D745471D6C`. Its app-owned DEX classes were inspected without executing the APK or contacting its server. The installed phone's exact build has not been matched to this hash.

**Android source evidence:** The exact two warning lines reported by the user exist in AOSP Permission Controller resources under `enhanced_confirmation_dialog_title_settings_default` and `enhanced_confirmation_dialog_desc_settings_default`. This identifies the stock warning family as **Enhanced Confirmation Mode (ECM) / Restricted Settings**, rather than establishing a Play Protect scan verdict. [Permission Controller strings](https://android.googlesource.com/platform/packages/modules/Permission/+/refs/heads/main/PermissionController/res/values/strings.xml)

ECM keeps a restriction state for the app. Displaying its denial dialog marks the app eligible for clearance but leaves access restricted. A separate `clearRestriction()` operation changes that state. The service's decision uses the protected setting, app state, and install trust; it does not count the number or direction of previously granted checklist permissions. Its state-changing methods enforce a system permission that ordinary permission grants do not supply. [AOSP ECM service](https://android.googlesource.com/platform/packages/modules/Permission/+/5e9f18aad4fd5167abadffd9d67fb90f90d45b3c/service/java/com/android/ecm/EnhancedConfirmationService.java)

The App info implementation invokes clearance in response to the user's restricted-settings action, through its screen-lock confirmation flow. Clearing ECM permits the borrower to request the protected access; it **does not automatically grant overlay, Accessibility, or Device Admin**. Each access still needs its own Android grant. These upstream sources explain the mechanism; they are not a runtime trace of the unknown OEM build. [AOSP App info clearance change](https://android.googlesource.com/platform/packages/apps/Settings.git/+/a8d381dce0dbe371cd2fdd4f804186dcdf7ef007%5E2..a8d381dce0dbe371cd2fdd4f804186dcdf7ef007/), [AOSP denial-dialog implementation](https://android.googlesource.com/platform/packages/modules/Permission/+/5693f485645dfc06571b9400a6d0cf4aa6c48b52/PermissionController/src/com/android/permissioncontroller/ecm/EnhancedConfirmationDialogActivity.kt)

**Interpretation of the reported success:** The later manual test confirms that explicit restricted-settings approval resolves the block on the tested phone. An approval during the earlier App info/Accessibility journey would also explain later overlay availability in the original sequence, but that chronology remains unconfirmed. If the original sequence truly worked without that approval, an OEM inconsistency, a previously cleared app state, or a difference in installed build needs investigation. If only the sample's green tick changed then, its result-handling branch is another candidate.

**Focused verification:** On a dedicated test phone, record every Settings page and confirmation during the same install's grant sequence, and record the actual overlay state before and after each step. In particular, record whether the Location row opened App info, whether the restricted-settings action was available and selected, and whether Android's overlay switch really changed. A separately approved clean-install comparison can check another grant order on the same model/build. If the system grant changes without explicit clearance, retain the trace for the senior developer/OEM to review; do not generalize it into an enrollment guarantee.

**CredNexa implication:** The running APK should detect missing overlay access, explain Android's user-controlled confirmation when encountered, and verify the grant afterward. Adding unnecessary Location, Usage Access, or Accessibility requirements solely to reproduce King Locker's sequence has no support in the inspected code. The backend's fresh overlay capability rule remains the appropriate activation check; the server cannot clear ECM.

### Accessibility: manually allow restricted settings when Android blocks access

For a trusted sample app or a future approved feature that genuinely needs an Accessibility service, Android may disable the service toggle until the borrower approves restricted settings for that app. **The user confirmed on 13 October 2026 that the manual App info procedure resolved the overlay permission block on their Android 16 phone.** Accessibility is protected by the same Android restricted-settings mechanism, but a separate successful Accessibility-service activation was not reported.

1. Open **Settings → Apps → See all apps → the borrower app/King Locker** to reach **App info**.
2. Tap the **three-dot menu ⋮** and select **Allow restricted settings**. Proceed only if the user trusts the app and understands why access is needed.
3. Complete Android's confirmation, including any device PIN/pattern/password prompt shown.
4. Return to **Settings → Accessibility → Downloaded apps / Installed apps / Installed services** (the label varies by phone), select the app's service, and explicitly enable it if desired.
5. Return to the APK and recheck whether its specific Accessibility service is enabled. Approving restricted settings alone does not activate the service or grant overlay access; each needs its own Android switch. For overlay, return instead to **Apps → Special app access → Display over other apps → the app**, then check `Settings.canDrawOverlays()` after the user grants it.

If **Allow restricted settings** is absent, first attempt the blocked service/special-access toggle to display Android's denial warning, then reopen App info and check the menu. The stock denial dialog marks the app eligible for the clearance action. If the option remains unavailable, retain the incomplete status and investigate that phone's policy/OEM implementation rather than showing a successful grant. [Google's manual instructions](https://support.google.com/android/answer/12623953), [Android denial-dialog behavior](https://android.googlesource.com/platform/packages/modules/Permission/+/5693f485645dfc06571b9400a6d0cf4aa6c48b52/PermissionController/src/com/android/permissioncontroller/ecm/EnhancedConfirmationDialogActivity.kt)

This is troubleshooting guidance for a user-controlled Android setting. **Accessibility remains outside CredNexa's currently agreed required permissions**, and this guidance does not change backend activation requirements.

### Required access absent as its own row in the sample photos

- **Notifications:** Android 13+ uses `POST_NOTIFICATIONS` for non-exempt app notifications. CredNexa needs notifications for overdue reminders, command/user messages, and foreground-service visibility where applicable. Current activation requires `notificationsAllowed: true`. A received FCM message does not prove a notification appeared.
- **Camera:** Required only for the in-app QR scanner. It is a runtime grant requested before opening the scanner; a supported verified-link/manual-entry alternative could avoid it. The backend does not currently make camera status an activation field.
- **Internet/FCM and boot recovery:** Internet access and a valid FCM setup are implementation prerequisites, while `RECEIVE_BOOT_COMPLETED` is a manifest permission for recovery. They are not extra borrower-facing special-access toggles.

## Current backend contract and actual mismatch

1. `POST /api/app/running-enrollment/preview` returns `requiredCapabilities: ["notificationsAllowed", "overlayAllowed"]` and `requirementsVersion: 1`.
2. Final `POST /api/app/device/register` rejects a running activation unless those two booleans are `true` and `capabilities.observedAt` is within five minutes. This is an **APK-reported** observation; the server cannot independently grant or prove Android access.
3. After activation, `POST /api/app/device/capabilities` stores a fresh report. Operator controls use the last report (fresh for up to 24 hours): overlay for lock, notifications for reminders, and location grant plus consent/tenant enablement for Get Location. Device Admin, battery state, Usage Access, Write Settings, Accessibility, and OEM Auto Start are not current gates.
4. The location rule accepts `"foreground"` as sufficient for a remotely issued `GET_LOCATION`. If the business requirement is an unattended fresh fix, this may overstate availability while the app is in the background. Test on supported Android/OEM versions and tighten the rule or label it best-effort.
5. The agreed Device Admin purpose is **normal-uninstall friction**, not a screen-lock call. Request activation, but do not block running enrollment if the borrower declines. The current backend accepts `deviceAdminActive` as an optional observation and does not gate activation on it; the app must never report a one-time system screen lock for a running `LOCK` command.

## Recommendation before changing any enrollment gate

**Keep a complete, accurate permission/status screen, but do not mark all ten photo rows mandatory by default.** Make each row correspond to a named Android grant and a real feature. The immediate CredNexa checklist should include camera, notifications, overlay, Device Admin for the normal-uninstall step, and a clearly conditional location row. Device Admin is requested but may be declined without stopping enrollment. Battery optimization, Battery Power Usage, and OEM Auto Start can be guided recovery steps after device-specific testing. Usage Access, Write Settings, and Accessibility need a separately approved feature that actually uses them.

**Add a permission troubleshooting state to the APK checklist.** On Android 16, a downloaded APK may need the borrower's explicit **Allow restricted settings** decision in Android App info before the overlay switch can be used. The app should explain this only when the OS actually presents that gate and allow the borrower to make the decision. The reported bottom-to-top order may be retained as a test case for a specific phone, but it should not be presented as a guaranteed fix or a way around Play Protect. If a required grant cannot be obtained, show the exact missing access and Android status, retain the borrower's progress, and let support diagnose the OS message. The backend should continue rejecting activation when its required fresh capability report is false; it cannot override a device-level permission block.

If the product decides that additional named grants must block activation, update the APK and backend **together**: define the Android check, denial/revocation behavior, report field, preview `requiredCapabilities`, registration validation, `requirementsVersion`, consent wording, operator warning/action gating, and tests. Preserve the current owner-device contract and define how already enrolled running devices are treated. A single `allPermissionsGranted` flag or a tap-based green tick is insufficient because it hides which feature has failed and cannot prove the OS state.
