# Running-device backend API implementation

Status: implemented in the backend workspace on 2026-10-08 and reconciled for running temporary unlock on 2026-10-09. This is a handoff contract for the dealer app, admin panel, and new borrower app. The borrower APK's endpoint-level requests and responses are in [running apk backend api contract.md](running%20apk%20backend%20api%20contract.md). It has been checked with local lint and automated tests; no production database migration or live device run has been performed.

## Phase 1 — additive data and controlled rollout

- `enrollmentMode` is `DEVICE_OWNER_QR` or `RUNNING_APP` on borrowers, enrollment claims, devices, and consent. Missing values on old records mean `DEVICE_OWNER_QR`. New borrower requests that omit the field still choose `DEVICE_OWNER_QR`.
- `TenantPolicy.runningEnrollmentEnabled` and `runningLocationEnabled` both default to `false`. Enable a tenant with `PATCH /api/admin/tenants/:id/running-enrollment` and `{ "enabled": true, "locationEnabled": false }`. Enabling requires the running QR configuration and a published running-app consent version.
- Configure `RUNNING_ENROLLMENT_SECRET_KEY` (64 hexadecimal characters), `RUNNING_ENROLLMENT_LINK_BASE` (HTTPS link into the borrower app), and `RUNNING_ENROLLMENT_PACKAGE_NAME`. Keep the secret key stable so existing QR claims can be shown again.
- `npm run migrate:enrollment-modes` is a read-only report by default. `npm run migrate:enrollment-modes -- --apply` backfills missing modes and identifies duplicate borrower/device groups for review. Run it against a database backup during rollout, after deploying code that understands both modes.
- Consent versions are mode-specific. Create a running consent draft with `POST /api/admin/consent-versions` and `enrollmentMode: "RUNNING_APP"`; publish it with the existing publish endpoint. Version strings remain globally unique, so use a distinct running version string. Publishing one mode does not unpublish the other.

## Phase 2 — dealer registration and QR

- Existing `POST /api/distributor/users/register` (also available under `/api/tenant`) accepts optional `enrollmentMode`. The dealer form should default to `DEVICE_OWNER_QR`. One borrower still consumes one credit and receives the existing EMI schedule. A running response contains `enrollmentId`; an owner response retains `enrollmentToken`.
- In the dealer app's borrower list, **Generate QR** appears for an unlinked borrower. The dealer app reads saved `User.enrollmentMode` when the button is clicked; it does not choose the type again. Existing `POST /api/distributor/users/:userId/enrollment/qr` re-displays a valid QR. Keep the existing owner request/response for `DEVICE_OWNER_QR`; for `RUNNING_APP`, send `{ "enrollmentMode": "RUNNING_APP" }`. The running response contains `qrType: "RUNNING_APP_LINK"`, `qrText`, PNG data URL, and expiry. `rotate: true` revokes the previous unconsumed claim and creates a new one; if consent was already accepted, the borrower must repeat OTP and consent for the new claim. The old consent record remains in the audit history. A running borrower called by an old dealer client with no mode gets `409 DEALER_APP_UPGRADE_REQUIRED`; a mismatched mode gets `409 ENROLLMENT_MODE_MISMATCH`. A linked borrower is rejected by the backend and must not show this button.
- The older `POST /api/distributor/enrollment/qr` accepts owner tokens only. Owner provisioning QR format and response fields remain intact. Do not give the internal running claim identifier to this endpoint.
- The running QR carries a high-entropy secret in an HTTPS app link. The database stores a lookup hash and an encrypted copy for authorized re-display. Treat the QR and `qrText` as credentials: display them only to authorized dealer staff, avoid logging or caching them, and clear them when the page closes.
- **Generate QR compatibility check:** `GET /api/distributor/users` already returns each borrower's saved `enrollmentMode` and `isDeviceLinked`. The borrower-scoped QR route uses that saved mode and preserves the owner request/response. It now rejects the action when either `User.isDeviceLinked` is true or a Device record exists, including inconsistent records. API success logs redact both owner and running QR contents; the dealer-facing response remains unchanged. The running APK extracts `code` from the scanned QR locally and uses the existing preview/OTP/consent/register APIs, so no new enrollment endpoint or request field is needed for this scan-first flow.

## Phase 3 — borrower running-app activation

1. On first open, the running APK shows its QR scanner and requests camera access at scan time. Scan the running QR displayed from the dealer borrower-list action. Parse the HTTPS QR text locally, extract `code`, and reject an owner provisioning QR. Call `POST /api/app/running-enrollment/preview` with `{ "enrollmentToken": "<code>" }` to show the masked borrower and lender details. This does not claim the token.
2. Show the manual IMEI 1/IMEI 2 screen, then the permissions screen. Check actual Android grants. Activation requires notification and overlay access. Device Admin, battery exemption, usage access, settings write, accessibility, and OEM auto-start can be reported but are not blanket activation gates. Location is optional and separately gated. Camera is for scanning, not a backend final-activation gate.
3. Call existing `POST /api/app/consent/terms`, `/consent/initiate`, `/consent/verify-otp`, and `/consent/accept`, providing the same scanned code where those endpoints require `enrollmentToken`. OTP verification supplies the borrower access token. The running consent acceptance can include `locationConsentAccepted: true` when the borrower explicitly agrees to location. Otherwise it is `false`. Recheck required grants before registration so the capability observation is within the backend's five-minute limit.
4. Generate and persist a random URL-safe `activationRequestId` (16–128 characters) for the final registration request. It only identifies a retry; it is not an authentication credential. The existing borrower JWT from OTP/consent authenticates the app calls, as in QR-provisioned Device Owner onboarding.
5. On the borrower's final confirmation, call existing authenticated `POST /api/app/device/register` with body: `enrollmentToken`, `activationRequestId`, `requirementsVersion: 1`, manually entered `imei` and `imei2`, `capabilities` (`notificationsAllowed`, `overlayAllowed`, `observedAt`, optional other grants), `fcmToken`, and device/app information. Only a declared single-IMEI handset can omit `imei2`. Both entered IMEIs use a 15-digit checksum and must not already belong to an active device. The backend atomically consumes the claim, links the borrower, and creates an `ACTIVE` running device. A retry with the same `activationRequestId` returns the existing device.

Once linked, authenticated running-app requests under `/api/app` use `Authorization: Bearer <borrower JWT>`, the same convention as the existing owner app. The backend resolves `User.linkedDeviceId` for running-device calls. No additional installation-signature headers or installation challenge are implemented. This carries lower assurance: a valid borrower JWT is sufficient for protected app calls, so the APK must protect token storage and use HTTPS.

An OTP login for a previously linked running borrower returns the same device-login shape as the owner flow: an access token, linked device summary, and current sync data. The app should call `/device/sync` after login to reconcile state. A replacement handset still needs a reviewed re-enrollment process because registration will not silently create another linked device; OTP does not prove the original installation.

The running app should call `POST /api/app/device/capabilities` at startup, after a permission or FCM token change, and at least once every 24 hours. Lock, reminder, and location controls require capability data received within the preceding 24 hours. Continue existing JWT-authenticated ping, sync, and command acknowledgement calls. The backend records actual permission loss without rewriting the enrollment consent. The app should sync on startup and after every push; FCM is a wake-up hint and sync is authoritative.

## Phase 4 — management APIs and device states

- Dealer and admin device lists/details include `enrollmentMode`, and running devices include `allowedActions` for conditional controls. Dealer borrower lists include the mode. Running IMEIs are masked in device list/detail responses; `identifierSource: "BORROWER_ENTERED"` identifies the unverified origin.
- The existing dealer/admin lock, unlock, and temporary-unlock endpoints accept running devices. The backend reuses `ACTIVE`, `GRACE_PERIOD`, `LOCKED`, `TEMP_UNLOCK`, `RELEASE_PENDING`, and `RELEASED` states. Lock is an app overlay restriction, not Android kiosk. Running lock acknowledgement must report `appRestrictionApplied` and `lockOverlayShown`; full and temporary unlock require matching cleared flags. The `TEMP_UNLOCK` command carries `tempUnlockExpiresAt`, and the shared expiry job queues `LOCK` for running and owner devices. The running APK must also enforce the deadline locally while offline and sync on reconnect.
- Dealer reminder endpoints and `POST /api/admin/devices/:deviceId/emi-reminder` use existing `EMI_REMINDER` commands. For running devices the FCM data includes reminder content. `UPCOMING` follows the pending-EMI presentation: overlay and sound. `OVERDUE` remains notification-only. The app must acknowledge `presentationResult` as `OVERLAY_SHOWN`, `NOTIFICATION_POSTED`, or `DEFERRED`; an overlay result also includes a boolean `soundPlayed`. An overdue overlay acknowledgement is rejected. Automatic reminders continue for MANUAL dealers; MANUAL suppresses EMI cron auto-lock. Critical risk auto-lock remains a separate policy.
- Existing dealer/admin location request endpoints require running location to be enabled for the tenant, separately accepted in consent, and presently granted by the app. Each request checks these conditions and rejects unavailable access with 409. The location result still arrives only through a `GET_LOCATION` acknowledgement.
- Existing dealer/admin release endpoints require a settled EMI schedule. Running release clears the app restriction and stored FCM token on acknowledgement; the APK should clear local JWT/refresh state. Managed per-app restrictions (WhatsApp, caller/dialer, YouTube), security toggles, wipe, manual override, and owner testing actions reject running devices with `409 UNSUPPORTED_FOR_ENROLLMENT_MODE`. For automatic dealers the running lock overlay offers Pay Now and Temp Unlock; these reuse the current borrower payment and unlock-request APIs, with operator case resolution through the existing temporary-unlock route.
- Payment approval and dealer mark-paid paths reuse the existing unlock or final release transitions. Running payment approval skips owner-only restriction-clear commands. EMI cron uses the existing UTC date thresholds and DPD/grace timing. It scans schedules in pages, including running borrowers, and skips a running auto-lock when overlay capability is stale or unavailable.

## Compatibility and rollout checks

- Owner-mode registration, QR payload, OTP/consent, command handling, and FCM reminder format remain backward compatible. Older records missing a mode resolve to owner mode.
- The new mode is off for every tenant until explicitly enabled. Publish running consent and set the three environment values before enabling.
- The implementation uses MongoDB transactions for activation and the existing payment/release flows; deployment requires the same transaction-capable MongoDB setup as current registration.
- Test with the scenarios in `dry run.md`: both tenant modes, due and overdue reminders, Pay Now and Temp Unlock overlay flows, timed relock and payment supersession, release, permission revocation, QR re-display/rotation, duplicate IMEI, JWT-authenticated registration retry, and prohibited managed controls. No production test documents were created in this implementation turn.
- The current FCM worker and EMI cron still use their established command-delivery model. Before a high-volume pilot, add an atomic delivery claim and make concurrent reminder/lock creation idempotent across parallel cron instances. The local tests verify API logic and compatibility; they do not prove concurrency behavior against MongoDB/FCM.
