# EMI Shield plan: one dealer workflow for new and running devices

**Prepared:** 5 October 2026; API compatibility review updated 8 October 2026
**Status:** Implementation plan; no backend or app changes have been made  
**Audience:** Backend, dealer app, running-device app, super-admin portal, QA, product  
**Companion:** [Running-device APK analysis](running_device_apk_analysis_and_architecture.md)

## 1. Product decision and scope

The dealer/tenant app should register a borrower once, then let the dealer choose **New device (Device Owner QR)** or **Running device (app enrollment QR)**. Both choices create the same borrower, EMI schedule, consent record, device record, command history, and audit history. The QR payload and what can actually be enforced differ.

Both the dealer app and super-admin panel should present the five original running-device controls—**Lock, Unlock, Send reminder, Get location, Release**—and the existing **Temporary unlock** action and borrower case resolution where authorized. They should use the same API/domain rules as the existing managed-device controls, with an enrollment-mode and capability check on every operation. A running app must be labeled **lower assurance** throughout. Its “Lock” requests an app-controlled lock overlay while the EMI restriction is active and, if Device Admin is enabled, may make a separate one-time Android `lockNow()` call. A QR-provisioned Device Owner device uses its managed kiosk lock instead. The running overlay cannot prevent the borrower from unlocking Android with their credential, revoking grants, force-stopping, or uninstalling the app. “Unlock” removes EMI Shield's restriction and dismisses its overlay; it does not unlock Android's keyguard. **Temporary unlock reuses the existing `TEMP_UNLOCK` state and expiry job:** clear the running overlay until the saved deadline, then request the overlay again. The running app must also enforce that deadline locally while offline. For automatic dealers, the running lock overlay shows **Pay Now** and **Temp Unlock** buttons leading to the same borrower payment and unlock-request screens/flow as the managed app. For reminders, preserve the two existing experiences: **overdue = notification only**; **pending/upcoming = prominent reminder with sound**. A managed new device may show its existing kiosk presentation; the running app uses a separate, short reminder overlay with sound where Android permits it, never a Device Owner kiosk. [Android `lockNow()` reference](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#lockNow()).

**Working assumptions for this plan:** the existing credit charge remains **one credit when a borrower is registered**, whichever QR is chosen. The running app asks the borrower to manually enter IMEI 1 and IMEI 2 after consent, and uses the existing IMEI registration fields. Enrollment mode does not change `EMI_AUTOMATED` versus `MANUAL`; those are the tenant's payment-control modes. Keep the existing `Device.state` and `DeviceCommand.status` values; add no new lifecycle-state enum for this rollout. If product pricing changes, make that an explicit separate ledger/pricing change.

### Tenant control mode applies to both enrollment paths

Treat `enrollmentMode` (`DEVICE_OWNER_QR` or `RUNNING_APP`) and `TenantPolicy.deviceControlRules.mode` (`EMI_AUTOMATED` or `MANUAL`) as independent fields. Resolve the tenant's control mode once in the shared EMI scheduler and command policy; the running app consumes the same server-provided `deviceControlMode` and EMI configuration as the owner app. Do not create a second schedule or a running-device-specific definition of manual mode. Delivery and enforcement then depend on the enrolled app's capabilities.

| Tenant policy | Scheduled EMI reminders | Scheduled EMI grace/lock | Operator actions on either enrollment mode |
|---|---|---|---|
| `EMI_AUTOMATED`, `lockOnGraceExpiry=true` | Upcoming and overdue reminders on the existing schedule | Existing grace transition and final `LOCK` after the configured DPD/grace period | Authorized manual lock, unlock, reminder, location, and settlement-gated release remain available |
| `EMI_AUTOMATED`, `lockOnGraceExpiry=false` | Same scheduled reminders | Grace processing can continue; final scheduled EMI `LOCK` is disabled | Same authorized manual actions |
| `MANUAL` | Scheduled upcoming and overdue EMI reminders remain enabled on the existing schedule; a dealer/admin may also explicitly send one | No scheduled EMI grace transition or final EMI `LOCK` | Authorized manual lock, unlock, reminder, location, and settlement-gated release |

All scheduled and manual `LOCK` requests for a running app use the same `LOCK` command and existing device state, with a mode-aware capability check and separate acknowledgement of the app restriction, lock-overlay presentation, and one-time Android screen lock. `Device.state=LOCKED` means the server requested a restriction; it is not evidence of durable Android lock. A missing notification grant or offline app can prevent a reminder from being shown; expose that in command outcome rather than silently calling it delivered.

**Confirmed product decisions:** [`scheduledJobs.js`](../backend/src/jobs/scheduledJobs.js) queues upcoming and overdue reminders *before* it skips `MANUAL` tenants for scheduled EMI grace/lock. Keep that order and apply it to both enrollment modes. [`getBorrowerAppConfig`](../backend/src/services/tenantDeviceControl.service.js) already enables EMI details, payment history, and EMI notifications for `MANUAL`; keep these presentation flags for both borrower apps. Payment submission stays disabled. [`Tenant Mode.md`](../Tenant%20Mode.md) now reflects these decisions. `riskManagement.service.js` may separately queue a critical-security `LOCK` when `riskRules.autoLockOnCriticalSecurityRisk` permits it, including in `MANUAL`; keep that policy independent of EMI lock mode, show it clearly in dealer/admin UI, and apply the running-app capability gate there too.

### Important existing access-control gap

[`ensureDistributorAccess`](../backend/src/modules/distributor/distributor.controller.js) verifies `tenant_admin` and `distribute` capability. Lock, unlock, and location routes currently call it as well. A distribute-only outlet may therefore reach controls that project context says belong to the **credit originator** (`lend` capability). Before exposing the same actions to running devices, separate **onboarding authority** from **lending-control authority**:

- Registration and QR issuance: active tenant with `distribute`, scoped to its own tenant.
- Lock, unlock, reminder, location, and release: an active lender with `lend`, or a distributor with an explicit, narrowly scoped delegation from the lender. Do not infer authority merely from a parent-tenant relationship.
- Super-admin: existing override authority, mandatory reason, settlement/consent rules, and audit trail. An admin action is an exception, not a transfer of the lender's ordinary authority.

Where an outlet registers the borrower for a parent lender, persist **registering tenant** and **lender tenant** explicitly on the loan/device or resolve them through an auditable loan ownership record. Check the lender relationship on every command. Keep all reads scoped to the correct tenant/channel-partner relationship; do not expose borrower data because a user happens to share a mobile number.

## 3. Shared data model

### 3.1 Enrollment and device identity

Add one enum field, `enrollmentMode: DEVICE_OWNER_QR | RUNNING_APP`, to **`User`, `EnrollmentToken`, and `Device`**. `User.enrollmentMode` preserves the dealer's choice even when a token expires or is cancelled, so QR regeneration cannot guess the mode from the latest token or a client-supplied value. `EnrollmentToken.enrollmentMode` binds the QR secret to that choice; `Device.enrollmentMode` records the method actually used at final activation. Set all three in the existing registration/finalization transactions and reject any disagreement. This field is **not** a new device lifecycle state. Migrate existing borrowers, tokens, and devices to `DEVICE_OWNER_QR` after checking that they represent the current managed app; use an owner default for old registration requests and reject unknown enum values with HTTP `400`. Keep `deviceOwnerStatus` as an actual owner-status signal. For running devices, retain its existing `UNKNOWN` value and display “Not Device Owner” based on `enrollmentMode`; do not add a new owner-status enum value merely for display, or mark a running device `CONFIRMED`/`RELEASED` because a normal app reported success.

**Database rollout:** add these fields and defaults before the dealer app starts sending `RUNNING_APP`; backfill old `User`, `EnrollmentToken`, and `Device` documents in bounded batches, including unlinked borrowers and expired tokens. Resolve any existing multiple unused tokens per borrower before enforcing one active claim per borrower/tenant with a suitable index plus transactional issuance. Keep the existing `User.isDeviceLinked`/`linkedDeviceId`, EMI schedule, credit ledger, `Device.state`, and command statuses. Index mode with tenant/user where list filters need it. A QR reissue reads the persisted `User.enrollmentMode`, requires the token mode to match, and never changes borrower mode; a pre-activation change of type uses a separate audited cancel-and-switch operation, while a linked device needs the replacement flow.

Keep `Device.imei` required and `Device.imei2` optional in the schema. For `DEVICE_OWNER_QR`, the owner app may populate them from Android where authorized. For `RUNNING_APP`, show **IMEI 1** and **IMEI 2** entry fields after OTP and consent; explain where to find the values in Android settings. Require both values when the handset presents two; if it genuinely has only one, record IMEI 2 as absent instead of inventing a value. Normalize digits, validate format/check digit where applicable, ensure the two entries are different, and flag duplicates against either IMEI field on another active device for dealer review. Show masked values to the dealer for visual confirmation against the target phone before handover. Record `identifierSource=borrower_entered` in enrollment/audit metadata. Android 10+ generally restricts direct IMEI access to privileged or specially eligible apps, so **manual entry is not device verification**. The app must not claim it read or attested those numbers. [Android identifier rules](https://developer.android.com/about/versions/10/privacy/changes#non-resettable-device-ids).

Use the existing borrower JWT from OTP/consent for authenticated app calls. The typed IMEI remains the familiar inventory/search field; it is not a credential or proof that the app runs on the phone whose IMEI was entered. FCM token, phone number, and Android ID are also insufficient alone. No per-installation cryptographic proof is implemented, so a stolen valid borrower JWT can call app APIs. Google's Play user-data policy restricts linking persistent identifiers such as IMEI to personal data, with limited exceptions including Device Owner management. A normally installed running app does not gain that exception through manual entry. Treat Play distribution of this exact IMEI-linked flow as blocked until a specific policy review establishes eligibility; the stated downloaded-APK channel still needs privacy/consent review. [Google Play User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311).

Extend the token with **`enrollmentMode`**, a hash for verifying newly issued running codes, and an encrypted copy of the QR secret for authorized re-display of an active code. A hash alone cannot recreate the same QR after a dealer reloads the screen. Encrypt the recoverable secret with a managed key; never store a running secret in plaintext. Reuse the token's existing `userId`, `tenantId`, `createdBy`, `expiresAt`, `consumedAt`, `cancelledAt`, `regeneratedFrom`, and `regeneratedTo` fields rather than storing duplicate identities or a second reissue chain. Return the raw running activation secret only inside the authenticated QR issue/re-display response; preview and final registration verify its hash. Do not include it in ordinary list/detail/audit responses or logs. The QR contains an opaque, short-lived app link and no borrower name, phone number, EMI amount, or server credentials. App-link install fallback must preserve the one-time claim safely.

The existing `User.isDeviceLinked`/`linkedDeviceId` suggests one active device per borrower. Maintain that product rule for the first release. A replacement must be a separate audited operation that invalidates old sessions where supported, command queue, FCM token, and activation token. Resolve running sync/ack through the JWT's borrower and exact `linkedDeviceId`, rather than `Device.findOne({userId})`, so it cannot select a prior or unrelated device. The JWT remains the sole app-call authenticator.

### 3.2 Reuse the existing states and command results

Keep [`DEVICE_STATES`](../backend/src/constants/deviceStates.js) (`ACTIVE`, `GRACE_PERIOD`, `LOCKED`, `TEMP_UNLOCK`, `UNLOCK_PENDING`, `OFFLINE_PENDING`, `CONSENT_INVALID`, `RELEASE_PENDING`, `RELEASED`) and the existing `DeviceCommand.status` values (`pending`, `sent`, `acknowledged`, `failed`, `expired`). Do not create `READY`, `LIMITED`, `STALE`, `PARTIAL`, or a second lock-state machine in MongoDB. Use `EnrollmentToken` expiry/consumption, `User.isDeviceLinked`, consent, `Device.state`, `desiredPolicyVersion`, `lastAppliedPolicyVersion`, latest command and its `ackPayload`, `lastSeenAt`, and `lastSyncAt` as the source of truth. Enrollment readiness and warning text can be **derived API/UI fields**, not persisted states.

Add only a timestamped capability snapshot (`deviceAdminActive`, `screenLockAvailable`, `notificationsAllowed`, `overlayAllowed`, `locationGrant`, `appVersion`, `sdkInt`, `observedAt`, `serverReceivedAt`) and compute effective actions server-side. A client report is not proof of device control; expire stale reports. Keep location permission separate from consent and distribution eligibility. Record the actual running lock outcome (`appRestrictionApplied`, `lockOverlayShown`, `screenLockCalled`, failure reason, observed time) in the existing `DeviceCommand.ackPayload` instead of introducing a new command or state enum.

`Device.state=LOCKED` remains the requested business/policy state. For running devices, the operator view pairs it with the latest relevant command's existing status and ack details: “Lock queued,” “Lock overlay reported shown,” “Screen lock called,” or “Result unknown/offline.” An acknowledgement does not prove the whole phone is unusable. For owner devices, retain present state behavior and show the same command-result detail where available.

### 3.3 State transitions for a running-device enrollment

Registration ends in the existing `ACTIVE` state once the token, OTP, consent, JWT, and required capabilities are validated. QR issuance and the steps before device creation live on `EnrollmentToken`/`User` records; they are not device states. Tenant control mode is also not a device state. The same state machine is used for owner and running devices, but the running app reports a weaker enforcement outcome.

| Existing `Device.state` | When it applies to the running app | What the operator should see |
|---|---|---|
| `ACTIVE` | Successful enrollment, or an `UNLOCK` acknowledgement that cleared the app restriction | Active; show last sync and permission health separately |
| `GRACE_PERIOD` | The existing EMI scheduler enters grace for an `EMI_AUTOMATED` tenant | Grace period; app must apply any supported grace UI/policy and acknowledge the `POLICY_UPDATE`; no grace transition for `MANUAL` |
| `LOCKED` | A scheduled/manual/risk `LOCK` was requested; the server currently sets this before app acknowledgement | “Lock requested” until the command result is known; after acknowledgement, show app restriction, lock-overlay presentation, and Android screen-lock outcomes separately |
| `UNLOCK_PENDING` | Dealer/admin/payment flow queued `UNLOCK`; `ACTIVE` follows a successful app acknowledgement | “Unlock pending”; do not imply the app restriction has cleared while offline |
| `TEMP_UNLOCK` | Existing timed exemption applies to both enrollment modes. | For running devices, clear the lock overlay after a valid `TEMP_UNLOCK` command and record the expiry. The app locally re-shows the overlay when the deadline passes and syncs; the shared expiry job changes requested state to `LOCKED` and queues `LOCK`. A payment/full unlock/release supersedes the timer. |
| `RELEASE_PENDING` | Settlement-gated `RELEASE_DEVICE` was queued | Release pending until the app completes local cleanup and acknowledges, or an audited recovery process resolves an unreachable installation |
| `RELEASED` | Successful running-app release acknowledgement | Financing controls ended; do not set or display Device Owner release status for this app |
| `OFFLINE_PENDING`, `CONSENT_INVALID` | Existing enum values, but no general transition currently writes them in the normal command paths | Do not repurpose either as a QR step, permission-warning label, or proof of lock failure. Derive offline/consent warnings from last contact, consent, capability, and command data unless a dedicated transition is implemented |

`EMI_REMINDER` and `GET_LOCATION` do not change `Device.state`. A missed reminder, stale location, revoked Device Admin grant, or failed lock is a command/capability outcome, not a new lifecycle state. The current backend sets `LOCKED` before a `LOCK` ack and `TEMP_UNLOCK` before its ack; a failed or expired command can therefore leave a desired state that was never applied. Add a reconciliation rule and tests for failed, offline, duplicate, and out-of-order commands: preserve the server's requested policy, report `pending`/`failed`/stale enforcement separately, and advance applied-policy evidence only after a valid acknowledgement. On reconnect the running app fetches the latest desired policy version, ignores superseded commands, and reports what it actually applied. The admin/dealer UI must never convert a requested state into a claim that the Android phone is secured.

## 4. One dealer onboarding experience, two QR formats

1. Dealer enters borrower/loan details as today and chooses **Enrollment type** on the Add Borrower form: **New device** (preselected) or **Running device**. Show concise capability/assurance differences before submission. Submit the value with the borrower form, persist it on `User` and the first `EnrollmentToken`, and show the saved choice on borrower detail and QR screens; it is independent of the tenant's `EMI_AUTOMATED`/`MANUAL` control mode.
2. `POST /distributor/users/register` accepts optional `enrollmentMode`. Omission defaults to `DEVICE_OWNER_QR` for older dealer builds; an invalid value fails instead of falling back. Existing one-credit debit and EMI schedule creation remain once per borrower. Return the saved mode and token expiry, plus the existing owner response fields for owner requests and an operator-safe enrollment ID for running requests.
3. In the dealer **borrower list**, show the existing **Generate QR** action only when the borrower is not linked to a device. The button reads stored `User.enrollmentMode`; it does not choose or change the mode. A mode-aware QR service issues at most one usable token for that borrower and saved mode. Keep `POST /distributor/enrollment/qr` **owner-only** for the legacy token-based flow. Reuse **existing** `POST /distributor/users/:userId/enrollment/qr` for both modes: an omitted request mode retains its present owner behavior when `User.enrollmentMode=DEVICE_OWNER_QR`; a running borrower requires an explicit `enrollmentMode=RUNNING_APP` from a compatible dealer app, which must match the stored user/token mode. An old client that omits mode for a running borrower gets a stable upgrade/mode error, never an owner QR. The running response has `qrType`, `qrText`, `qrCodeDataUrl`, expiry, and an operator-safe status, with no Android provisioning extras or redundant raw-token field. The existing owner response shape stays intact.
4. **New-device path:** current Android setup/provisioning QR and Device Owner borrower app continue. Record actual owner confirmation during enrollment.
5. **Running-device path:** the borrower downloads/opens the separately signed app and its QR scanner. The app requests camera access at scan time, scans the running QR displayed by the dealer borrower-list action, parses `qrText` locally, and sends the opaque `code` to the preview API. Reject the owner Android provisioning QR. Show the backend-verified lender/borrower preview, then collect IMEI 1 and IMEI 2 (or a real single-IMEI exception). Next show the access checklist. Each button opens the relevant Android permission or special-access screen; on return, recheck the actual grant. Include notification access for reminder delivery, **Draw over other apps** (`SYSTEM_ALERT_WINDOW`) for running lock/reminder overlays, and optional Device Admin with `force-lock` for a separate `lockNow()` action. Do not require unrelated Accessibility, Usage Access, Write Settings, SMS, contacts, Auto Start, or battery exemptions. Camera is for scanning but is separate from the backend's final activation gates. Then complete existing OTP and mode-specific versioned consent bound to the same scanned code. Recheck required grants immediately before Finish because the backend requires a fresh capability timestamp. The final **OK / Finish enrollment** button is enabled only when the required grants are currently present; a tap, Activity result, or stored preference is not proof of a grant.
6. **Final activation is one commit after OK:** the app submits the exact scanned code, borrower JWT, borrower-entered IMEIs, stable body `activationRequestId`, FCM token, and a freshly observed capability snapshot. Only then does the backend validate the required-capability policy, atomically create the `RUNNING_APP` device in `ACTIVE`, consume the token, and link `User.isDeviceLinked`/`linkedDeviceId`. If the app closes, a grant is denied, or the network fails before commit, consent may exist but there is **no enrolled device** and the dealer cannot send device controls. A retried final request with the same ID returns the same device; a different ID after linkage conflicts. The dealer visually confirms the masked IMEI values and linked borrower before handover.
7. Dealer app polls an enrollment-ID-based status endpoint. Derive operator text such as “QR active,” “OTP/consent pending,” “Awaiting final activation,” “Device linked,” “Access lost,” or “Expired” from existing token/user/consent/device fields and any optional pre-activation progress telemetry; these are **presentation labels**, not new `Device.state` values. Without pre-activation telemetry the dealer can see only consent complete versus final device linked, which is sufficient for the first release. A linked running app is not Device Owner. Use an operator-safe enrollment ID in polling instead of placing the raw activation secret in URLs.
8. The existing borrower-scoped QR route keeps its current **reuse valid token / replace expired token** behavior when `rotate` is absent, preserving owner clients. A new `rotate: true` request explicitly cancels the unused current token and issues a new mode-bound token atomically, with actor/reason and old/new token IDs in audit; a running app already using the old QR must restart its claim. Rotation never charges another borrower credit or switches enrollment mode. A mode change before device binding is a distinct audited cancel-and-switch action. Once linked, changing mode requires a controlled device replacement/re-enrollment workflow.

**QR regeneration API contract:** keep `POST /api/distributor/users/:userId/enrollment/qr`. An empty body retains the existing owner behavior for a borrower saved as `DEVICE_OWNER_QR`. A compatible dealer app sends `{ "enrollmentMode": "RUNNING_APP" }` to show/reuse a running QR or `{ "enrollmentMode": "RUNNING_APP", "rotate": true }` to invalidate and replace it. The mode in the request is a compatibility guard, **not** the source of truth; compare it with `User.enrollmentMode` and the token mode. A no-mode request for a running borrower returns HTTP `409` with `DEALER_APP_UPGRADE_REQUIRED`; a mismatched explicit mode returns HTTP `409` with `ENROLLMENT_MODE_MISMATCH`. The owner response keeps its current `qrPayload`, `qrCodeDataUrl`, `enrollmentToken`, and `tokenExpiresAt` fields. The running response returns `enrollmentMode`, `qrType=RUNNING_APP_LINK`, `qrText`, `qrCodeDataUrl`, `tokenExpiresAt`, and `reusedExistingToken`; its `qrText` contains the one-time secret, but the response has no Android `PROVISIONING_*` keys or separate `enrollmentToken`/`oldEnrollmentToken` field. Reuse the existing auth, tenant scoping, device-linked rejection, transaction, and audit path, with mode checks added before any mutation.

The owner `registerDevice` path historically finds an active token by user without requiring the secret in its request. The running branch requires the exact scanned running code and checks token user, tenant, **mode**, expiry, cancellation, consumption, OTP, consent, and JWT. Reuse IMEI storage, device creation, and the `User.isDeviceLinked` transaction; add manual-identifier provenance. Preserve the legacy owner path without requiring an owner-app update. Never let an owner token register a running app or vice versa. The ID-based running status response omits the raw token.

**Permission checklist evidence:** the [APK analysis photo addendum](running_device_apk_analysis_and_architecture.md#photographed-checklist-and-emi-shield-enrollment-decision) maps all ten rows in the user-provided screenshots. The photos show only **Write Setting** green and nine rows red; they do not prove Android grant state or specify what the generic **Runtime Permission** contains. Product decision: **only access needed for the agreed features can block enrollment**. Request camera at the in-app scan step; present separate, named checks for notification, overlay (used for running lock and pending/upcoming reminder), Device Admin, and conditional location afterward. Camera permits scanning but is not a backend final-activation grant. Treat the two battery rows, Usage Access, Write Setting, Accessibility, and Auto Start as nonblocking unless a later feature review establishes a specific need and policy basis. Do not create a single “all permissions granted” boolean from the screenshot's green/red icons.

## 5. Five running-device actions

| Action | Existing backend route/service | Running-device meaning and backend gate | Operator result to display |
|---|---|---|---|
| **Lock** | Dealer `POST /distributor/devices/:id/lock`; admin `POST /admin/devices/:deviceId/lock`; automated jobs also queue `LOCK`. | Require valid consent, lender authority or audited admin override, active enrollment, no release, and a current capability snapshot. Reuse `LOCK`; the running app enters its EMI-restricted state and presents the lock overlay when Android permits. If Device Admin is active, a separate one-time `lockNow()` call may occur. Record app state, overlay presentation, and screen-lock call separately in `ackPayload`. | `Queued → delivered → lock overlay reported shown`, plus `screen lock called` if true. If overlay is unavailable, report failure/limited enforcement, not success. Never say “phone unusable.” |
| **Unlock** | Dealer/admin `UNLOCK` routes; payment approval and other paths also queue unlock. | Authorization and policy/version checks remain. Clear the running app's EMI-restricted state, dismiss its lock overlay, and cancel any pending/superseded lock locally; reconcile latest server state. It cannot dismiss Android keyguard. This action must still work when Device Admin has been revoked. | `Unlock requested → app restriction and overlay cleared`; show pending/offline until observed. No temporary-unlock timer is started. |
| **Send reminder** | Dealer overdue/upcoming reminder routes; `queueEmiReminder`; admin has testing/custom notification paths but no dedicated normal EMI reminder action. | Reuse `EMI_REMINDER` and its `reminderType` with validated amount/due-date/schedule context. `OVERDUE` remains a notification-only flow. `PENDING`/`UPCOMING` follow the existing prominent reminder flow: managed owner app keeps kiosk + sound; running app attempts a short, dismissible overlay + sound with a notification fallback. Rate-limit and deduplicate. | Show command delivery and actual presentation separately: notification posted, overlay shown, sound played/suppressed, fallback, or failed. | **Get location** | Dealer/admin `location-request`; `queueGetLocationCommand`; location accepted only on matching `GET_LOCATION` ack. | Require explicit, current consent; authorized actor/purpose; valid location capability; request expiry; and a distribution-policy gate. ### 5.1 Device visibility and enforceable control matrix

### 5.2 Two reminder presentations, one command contract

`EMI_REMINDER` already carries `payload.reminderType` (`OVERDUE`, `PENDING`, `UPCOMING`). Do not introduce a new command or device state. The dealer and admin **Send reminder** action should present two understandable choices and validate the actual EMI schedule server-side:

| Reminder choice | Current managed Device Owner app | New running app |
|---|---|---|
| **Overdue EMI** (`OVERDUE`) | Existing notification-only experience | Post a standard borrower notification only. No kiosk or overlay and no separate app-controlled alarm sound; Android may still play the notification channel's chosen sound. |
| **Pending/upcoming EMI** (`PENDING` or `UPCOMING`) | Existing kiosk reminder screen plus sound | Attempt a brief, dismissible `TYPE_APPLICATION_OVERLAY` reminder plus sound, showing the EMI context and an open-app/payment action. This is a presentation, not a lock: it must not cover emergency/system UI, block touch outside the reminder, or repeatedly relaunch to defeat dismissal. If overlay is unavailable, post a prominent notification on the reminder channel; sound follows Android/user audio and channel settings. |

Existing production dealer and scheduler paths currently emit `UPCOMING` for an upcoming installment; `PENDING` is a supported enum but is not emitted by those production routes. If product adds a distinct pending-EMI trigger, give it the same running presentation as `UPCOMING` and validate that it targets a pending installment. Dealer overdue/upcoming routes remain separate and the new admin reminder route must accept only a validated choice. The server derives the desired presentation from `Device.enrollmentMode` plus `payload.reminderType`, not from a client-supplied “show kiosk” flag.

For running devices, include the overlay grant in the enrollment/capability checklist because this is now a chosen feature. Android requires explicit user approval for `SYSTEM_ALERT_WINDOW`; the app checks `Settings.canDrawOverlays()` before showing anything. An approved overlay is **not** a guarantee of immediate display from a force-stopped or backgrounded app, and Android places further limits on background service starts. Use FCM only to wake the app; it fetches the authenticated `EMI_REMINDER`, applies one presentation for that command ID, and reports `presentationResult` (`OVERLAY_SHOWN`, `NOTIFICATION_POSTED`, `DEFERRED`, or `FAILED`), `soundResult` (`PLAYED`, `SUPPRESSED`, or `FAILED`), grant state, timestamp, and failure reason in the existing `ackPayload`. Never report sound as played solely because the server requested it. The app must respect silent mode, Do Not Disturb, user channel settings, and borrower dismissal. [Android overlay permission](https://developer.android.com/reference/android/Manifest.permission#SYSTEM_ALERT_WINDOW), [background foreground-service limits](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [notification channel controls](https://developer.android.com/develop/ui/compose/notifications/channels).

The current [`queueEmiReminder`](../backend/src/services/emiReminder.service.js) creates an `EMI_REMINDER` command and, for `UPCOMING`, can also enqueue a visible `NOTIFICATION` command; its FCM reminder push is data-only. Make that companion notification mode-aware so a running app does **not** show a duplicate notification alongside the overlay. If the overlay cannot be shown, the running app posts the single fallback notification for the same source command ID. Overdue has no companion visible-notification command in this service, so the running app must post its overdue notification after authenticated sync. Deduplicate by device, installment, reminder type, and source command ID across FCM repeats and retries. Neither reminder type changes `Device.state`. Test foreground/background, overlay granted/denied/revoked, notifications muted, silent/DND, offline replay, duplicate FCM, and Android/OEM restrictions; surface the actual result in both operator apps.

### Lock contract must be honest

`DevicePolicyManager.lockNow()` is an immediate screen lock available to an active Device Admin that declared `force-lock`; it does not create a persistent lender-owned kiosk. If there is no secure device credential, the API can only put the device to sleep. The user can unlock it with their credential, and Android can limit background activity launches. Define running-mode success as **the app's own restriction applied and lock overlay actually shown**, with a separate **system screen-lock call outcome**. The lock overlay is distinct from the brief pending/upcoming reminder overlay and from the managed-device kiosk; if it cannot appear, report reduced enforcement. Do not use Accessibility to prevent users disabling security settings or uninstalling. [Android `lockNow()` reference](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#lockNow()), [background activity launch limits](https://developer.android.com/guide/components/activities/secure-bal).

### Location release gate

Google Play's current Financial Services policy prohibits `ACCESS_FINE_LOCATION` for personal-loan and related app categories, including certain facilitator/accessory apps. Device-finance classification and distribution need a specific product/policy decision before promising running-device location. If that classification applies, do not put prohibited fine-location permission in the Play build; assess whether a disclosed approximate, user-initiated flow is eligible and useful. Android also restricts location foreground services started while an app is in the background. Thus **Get location is a conditional product action**, and the portal/dealer app must hide or disable it when the published app cannot support it. [Google Play Financial Services policy](https://support.google.com/googleplay/android-developer/answer/9876821), [Android background location limits](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

## 9. Cron system review for running devices

The same scheduled infrastructure can serve both enrollment modes; **do not create a second running-device EMI cron**. Firebase exports six scheduled functions in [`backend/index.js`](../backend/index.js), and standalone development uses matching timers in [`scheduledJobs.js`](../backend/src/jobs/scheduledJobs.js). Production cadence is FCM delivery every minute; temporary-unlock expiry every 10 minutes; SLA escalation and EMI policy every 30 minutes; manual-override renewal and tenant-metrics reconciliation daily. The scheduled policy is currently mode-blind at the device level, so it is **not launch-ready for running devices without the gates below**.

| Job | Current effect | Running-device decision / required change |
|---|---|---|
| `emiPolicyJob` | Finds due/overdue schedules, calculates overdue amount/DPD, queues 10-day and 5-day `UPCOMING` reminders, grace `POLICY_UPDATE`, 12-hour `OVERDUE` reminders, and final `LOCK` after DPD + grace. | Reuse financial calculations and tenant `EMI_AUTOMATED`/`MANUAL` settings. Both modes receive automatic reminders, while MANUAL still skips EMI grace transitions and EMI auto-lock. Route `UPCOMING` to running overlay + sound and `OVERDUE` to notification only. Apply the running command/payload allowlist and capability/consent gate before each queue or state change. Distinguish requested `LOCKED` from acknowledged running enforcement. Do not generate owner restrictions in a grace update. |
| `fcmDeliveryJob` | Sends pending/retryable `DeviceCommand` FCM plus app notification jobs. `EMI_REMINDER` is a data-only push; `UPCOMING` can also have a companion visible `NOTIFICATION`. | Resolve the linked device and mode, reject/expire owner-only commands for running devices, and avoid the duplicate upcoming notification described in §5.2. FCM `sent` is transport status, never proof of overlay, sound, notification, or lock. The running app fetches commands and acknowledges actual result. |
| `tempUnlockExpiryJob` | Finds all expired `TEMP_UNLOCK` devices, sets `LOCKED`, and queues `LOCK`. | Include running devices. **Correctness fixes needed for both modes as the fleet grows:**

1. [`runEmiPolicyJob`](../backend/src/jobs/scheduledJobs.js) skips a schedule entirely when there is no `Device`, before updating overdue installments and DPD. Move financial recalculation ahead of device lookup so an enrolled borrower awaiting final running-app activation still has correct loan records; device commands remain conditional on an active linked device.
2. The EMI query uses `.limit(500)` without a stable sort/cursor. A sufficiently large eligible set can cause the same first batch to be scanned every 30 minutes while other schedules starve. Add stable pagination or claimed work partitions and a supporting due-date/status index; measure scan lag per tenant/mode.
3. Reminder existence checks and command creation are separate writes; overlapping Firebase invocations, a manual cron endpoint, and the local timer can race. Add a durable idempotency key/unique index for schedule + installment + reminder type + reminder window, plus an atomic command/outbox transition for grace and lock. Current grace/lock paths update `Device.state` before creating their command, so a crash can leave an unissued desired state. Guard release states and stale policy versions in the same transition.
4. The FCM worker reads candidate commands before marking them `sent`, with no atomic claim; concurrent workers can send duplicates. Claim each delivery atomically, then retry with bounded backoff. The worker currently uses a hard-coded five retries while `DeviceCommand.maxRetries` also exists; after exhaustion it can leave an `EMI_REMINDER` pending without another attempt. Use the stored limit and a terminal outcome. A `sent` command with no app acknowledgement must remain visible and recoverable by authenticated sync, with an explicit stale/expiry signal; do not mark it applied.
5. `buildPolicyUpdateMessage` falls through to a generic `POLICY_UPDATE` payload for unrecognized command types. For running mode, reject unknown or owner-only command types/payloads at queue, delivery, and sync boundaries rather than transmitting them as a generic policy. Retire incompatible pre-existing pending commands during migration.
6. Calendar math in the EMI job uses **UTC days** (`startOfUtcDay`) even if `SCHEDULER_TIME_ZONE` is set to India time. Keep UTC calendar dates for both enrollment modes as the confirmed compatibility contract. `SCHEDULER_TIME_ZONE` controls invocation time only; it must not silently change due-day, DPD, reminder, or lock thresholds. Test near UTC midnight and date boundaries so both enrollment modes receive the same decisions for the same loan.
7. Verify production FCM configuration before launch: [`fcmDeliveryWorker.js`](../backend/src/jobs/fcmDeliveryWorker.js) uses mock delivery unless `FCM_MOCK_MODE` is exactly `false`. A mock result currently looks like a sent provider message. Mark mock delivery distinctly in monitoring and do not count it as borrower reachability. Firebase scheduler has `retryCount: 0`; each job therefore needs resumable, idempotent work on the next scheduled run.

**Confirmed overdue cadence:** keep the existing timing for both enrollment modes. The cron sends automatic `OVERDUE` reminders every 12 hours only while an installment is in the configured DPD/grace window, and skips them while the device is already `LOCKED` or in an active temporary unlock. It does not begin them immediately when an installment first becomes overdue, or continue them after grace expiry. Label this timing accurately in dealer/admin copy and monitoring; do not imply that the first overdue day triggers a notification.

**Cron acceptance checks:** one owner and one running device under the same automated tenant receive the same UTC due-day selection, but their `UPCOMING` presentation differs; `OVERDUE` is notification-only; `MANUAL` receives automatic upcoming/overdue reminders but no EMI grace transition or EMI auto-lock; critical-risk auto-lock remains separately governed by `riskRules` and is visible in the UI; a missing device does not stop EMI accounting; no running manual-override token is created and expired running temporary unlocks queue relock; unsupported/stale commands are not delivered; missing FCM/permission grants and offline devices show truthful results; concurrency produces one logical reminder/lock; large backlogs progress past the first batch; owner-device cron behavior remains compatible.
